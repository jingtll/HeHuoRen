# ADR 0003：比赛目录的持久化与人工发布

状态：Accepted · 2026-10-04；实施依据为 Issue #22。

## 背景

首页需要可靠地查询比赛届次与多个赛段，不能将承办关系、资格范围和转载单位混为一谈。通知包含精确时间、仅日期、未知及冲突信息；一次录入可能同时更改多个实体和关系。当前仅交付公开查询及人工导入，不提前引入账号或管理端。

## 决策与权衡

使用 PostgreSQL、pg 和 Drizzle 定义本任务涉及的实体与关系。稳定 ID、实体归属、发布状态、排序日期、可计算的报名时间点与日期精度分列保存；其余展示属性使用各实体的 JSONB。承办、参赛学院、赛段来源采用独立关系表，来源与赛段以复合外键防止跨届引用。

替代方案是将所有展示属性立即拆为独立列，或直接持久化整套前端语料。选择当前形状可保留复杂规则原文并减少未知字段过早建模，同时以独立表和约束保护实体关系；代价是 JSONB 形状依赖导入校验，查询时间列和展示时间字段必须在同一事务同步。未来增加写接口时必须复用这些校验和事务，不允许直接更新一份时间表示。

数据库迁移使用按文件名记录的事务 SQL，导入以稳定 ID 合并实体，关系数组完整替换。文件缺项不表示删除。预览运行真实事务并回滚；已发布内容执行更新需显式确认，默认新届次为草稿，生产拒绝演示数据。

列表在一次只读一致快照内完成过滤、稳定排序、两类总数与分页，使用同一服务端时刻计算状态；关系条件使用 EXISTS。详情保留完整届次。公开 API 不抓取官网，不接收客户端业务时钟，不返回平台内部发布状态。

## 后果

- 官方来源、历史/演示标识与平台发布状态独立，未经发布的数据不出现在公开查询中。
- 测试使用独立 PostgreSQL 数据库及隔离 schema；生成 OpenAPI 不建立数据库连接。
- 迁移属于首次新增数据库模型；回退应用时保留数据，不自动删除业务表。
- JSON GET 契约可供未来 H5、微信小程序复用；Axios、相对地址、History 与 DOM 锚点迁移成本登记在迁移待办，目标端仍待实测。
